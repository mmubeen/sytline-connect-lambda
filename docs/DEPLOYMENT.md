# Deploying with the SAM CLI

Target: AWS GovCloud **us-gov-east-1**, one stack named `sytline-connect`, one configuration (`default`).
Everything below is run from the `src/` directory. This guide covers deploying the code; the network and ERP
prerequisites are listed in section 2 and come from
`docs/Instruction Sheet AWS GovCloud API Gateway to On-Premises Sy.docx`.

> **Status:** the template builds and validates locally, but it has not yet been deployed to a real account.
> The SyteLine web-service names (collections, methods, SOAP operations) are unconfirmed until the read-only
> discovery task (T013 in `specs/001-syteline-erp-integration/tasks.md`) has run. **Keep live ERP writes off.**

> **Two-stage job-number workflow** (reserve the CO and job numbers, then save with them) is part of this stack: see [RESERVATIONS.md](RESERVATIONS.md).

> **Testing a deployment step by step:** [TESTING.md](TESTING.md).

> **The SyteLine database calls** (numbers, customer search, defaults) and the route settings are described in [DATABASE.md](DATABASE.md).

> **No network available, and the ERP is reachable from the internet?** See the stand-alone version without any VPC: [STANDALONE.md](STANDALONE.md).

## 1. What gets deployed

| Resource | Purpose |
|---|---|
| `OrderApi` (private REST API, stage `prod`) | `POST /confirmed-orders`, `GET /upload-jobs/{id}`; IAM auth; callable only through the approved `execute-api` VPC endpoint |
| `IntakeFunction` | validates and records an order, starts the worker, returns an upload ID |
| `StatusFunction` | returns the state of an upload |
| `WorkerFunction` (in your VPC, reserved concurrency 1, no automatic retries) | runs the upload against the SyteLine web service |
| `SweeperFunction` (every 5 minutes) | re-drives `accepted` uploads, parks stale `running` ones as `needs_reconciliation` |
| `DirectFunction` (in your VPC) | direct-invoke actions: `health`, `add_note`, `get_notes` |
| `DepsLayer` (`sytline-connect-deps`) | zeep, lxml, requests, urllib3 built for Linux x86_64 / Python 3.13 |
| `JobsTable` (DynamoDB, on demand, point-in-time recovery, TTL) | uploads and the `request_ref` index |
| DynamoDB gateway endpoint, Secrets Manager interface endpoint | so the worker in private subnets can reach them (always created with a new host network; otherwise see `CREATE_VPC_ENDPOINTS`) |
| Host network (**only if you do not supply one**, section 3a) | VPC, two private subnets, a route table with no route out, security groups, and optionally the API-caller endpoint |
| IAM roles | one per function, least privilege (generated by SAM) |

## 2. Prerequisites

**Tools (on the machine that deploys)**
- AWS CLI v2 with credentials for the GovCloud account, ideally as a named profile (`aws configure list-profiles`; the `aws-us-gov` partition). Select it with `./deploy.sh --profile <name>` (section 4).
- SAM CLI (`sam --version`): <https://docs.aws.amazon.com/serverless-application-model/latest/developerguide/install-sam-cli.html>
  or `pip install aws-sam-cli`.
- `python3` with `pip` (any recent 3.x) and `make`. **Docker and a local Python 3.13 are not needed**: `src/Makefile`
  installs Linux wheels with pip's cross-platform flags.
- IAM permissions to create CloudFormation stacks, Lambda, API Gateway, DynamoDB, IAM roles, VPC endpoints and
  an S3 bucket for artifacts (SAM creates and manages that bucket: `resolve_s3 = true`).

**In the account (created before the first deploy)**
1. **Secret.** A Secrets Manager secret in us-gov-east-1 containing JSON with `SYTELINE_PASS`:
   ```
   printf '{"SYTELINE_PASS":"<password>"}' > /tmp/sytline-secret.json   # do not commit; delete afterwards
   aws secretsmanager create-secret --region us-gov-east-1 --name sytline/connect \
       --secret-string file:///tmp/sytline-secret.json
   shred -u /tmp/sytline-secret.json 2>/dev/null || rm -P /tmp/sytline-secret.json
   ```
   Note the ARN it prints (`arn:aws-us-gov:secretsmanager:us-gov-east-1:...`).
2. **API client path.** An `execute-api` **interface VPC endpoint** in the VPC the approved callers use; note its ID
   (`vpce-...`); the stack restricts the API to it. Alternatively, while creating the host network, the stack can create
   this endpoint inside the new network (`CREATE_API_ENDPOINT=true`, section 3a).
3. **Worker network: use an existing one or let the stack create it (section 3a).** Either way the functions need a
   route to the plant over the Site-to-Site VPN, outbound **HTTP port 80** to the SyteLine web service and HTTPS to the
   AWS endpoints, and plant DNS that resolves the SyteLine host from the subnets. **The plant connection is never created
   by this stack**: the network team makes it (instruction sheet, section 2: IKE/IPsec, routes, Palo Alto policy,
   return path). An existing network must already have it; a created network needs it added after the deployment.
4. **Account limits.** Reserved concurrency of 1 for the worker needs at least 100 unreserved Lambda concurrency left
   in the account.

## 3. Configure

`src/samconfig.toml` holds only the fixed settings (stack name, region, capabilities). Site-specific values live in
`src/deploy.env`, which is git-ignored and contains no passwords:

```
cp deploy.env.example deploy.env
```

| Variable (`deploy.env`) | Template parameter | Meaning |
|---|---|---|
| `AWS_PROFILE_NAME` | (none) | AWS credentials profile for every AWS-facing step; `--profile` overrides it; empty = default credential chain |
| `SYTELINE_WSDL` | `SytelineWsdl` | `http://<host>/IDORequestService/IDOWebService.asmx?wsdl` (HTTP, port 80) |
| `SYTELINE_USER` | `SytelineUser` | web-service user name |
| `SYTELINE_SECRET_ARN` | `SytelineSecretArn` | the secret from step 2.1 |
| `SYTELINE_CONFIG` | `SytelineConfig` | SyteLine configuration, default `CCT` |
| `SYTELINE_DEFAULT_WHSE`, `SYTELINE_DEFAULT_ORDTYPE` | `DefaultWhse`, `DefaultOrdType` | used when an order omits them |
| `IDP_STATE_MACHINE_ARN` | `IdpStateMachineArn` | optional: the IDP state machine whose `SUCCEEDED` events start the event intake (same account and region; needs the IDP settings); empty = nothing starts automatically. See [EVENT_INTAKE.md](EVENT_INTAKE.md) |
| `API_VPCE_ID` | `ApiVpcEndpointId` | existing `execute-api` interface endpoint; empty only with `CREATE_API_ENDPOINT=true` |
| `CREATE_API_ENDPOINT` | `CreateApiEndpoint` | `true` creates that endpoint in the **new** host network (create mode only); default `false` |
| `WORKER_VPC_ID`, `WORKER_SUBNET_IDS`, `WORKER_SG_IDS`, `WORKER_ROUTE_TABLE_IDS` | `WorkerVpcId`, `WorkerSubnetIds`, `WorkerSecurityGroupIds`, `WorkerRouteTableIds` | existing network: **all four** (lists comma-separated). All four empty: the stack creates the network |
| `HOST_NETWORK_CIDR` | `HostNetworkCidr` | create mode only, required, **no default**: IPv4 /16 to /25; must not overlap the plant range |
| `PLANT_CIDR_1`, `PLANT_CIDR_2`, `PLANT_CIDR_3` | `PlantCidr1`..`3` | create mode: plant range(s) the functions may reach on HTTP port 80 (1 required) |
| `DYNAMODB_PREFIX_LIST_ID` | `DynamoDbPrefixListId` | optional `pl-...`: limits HTTPS egress to DynamoDB to the managed prefix list |
| `CREATE_VPC_ENDPOINTS` | `CreateVpcEndpoints` | existing network only: `false` if the VPC already reaches DynamoDB and Secrets Manager (endpoints or NAT); ignored when the network is created |
| `LIVE_WRITES`, `LIVE_APPROVAL_REF` | `LiveWrites` | leave `false`; see section 7 |

## 3a. Network: use an existing one or let the stack create it

**Existing network.** Fill in all four of `WORKER_VPC_ID`, `WORKER_SUBNET_IDS`, `WORKER_SG_IDS`,
`WORKER_ROUTE_TABLE_IDS`. Nothing network-related is created, and the deployment behaves exactly as before. A partial set
is refused (by `deploy.sh`, and by CloudFormation rules before anything is created).

**Create the network.** Leave all four empty and set `HOST_NETWORK_CIDR` and `PLANT_CIDR_1` (no defaults). The stack
then creates:

| Created | Details |
|---|---|
| VPC | your `HOST_NETWORK_CIDR`, DNS support and hostnames on |
| Two private subnets | one /26 each, in the first two availability zones (a region with fewer than two is refused) |
| One route table | associated with both subnets, **local route only: no route to the internet and none to the plant** |
| Function security group | no inbound; outbound HTTP 80 to the plant range(s), HTTPS to the network's own endpoints and to DynamoDB (`0.0.0.0/0`, which has no internet route behind it, or only the prefix list if `DYNAMODB_PREFIX_LIST_ID` is given) |
| Endpoint security group | inbound HTTPS from the host network only |
| DynamoDB gateway endpoint, Secrets Manager interface endpoint | always, so the worker works with no internet |
| API-caller endpoint | only if `CREATE_API_ENDPOINT=true` (usable by callers in or peered with the new network; others still need their own endpoint and `API_VPCE_ID`) |

**Never created:** internet gateway, NAT gateway, elastic IP, default route, VPN gateway, VPN connection, or any route to the
plant.

**Warnings**
- Pick a `HOST_NETWORK_CIDR` that does **not overlap** the plant network or any network you will connect it to; the
  deployment cannot check this. Confirm it with the network team first.
- Until the plant connection exists, the health check **fails at `dns` or `tcp`**. That is expected, not a fault.
- Switching an existing stack between "create" and "supply" would replace the network the functions run in. `deploy.sh`
  reads the stack and refuses unless you pass `--allow-network-change`.

### Handover to the network team (create mode)
After the deployment, give them the stack outputs:
```
aws cloudformation describe-stacks --region us-gov-east-1 --stack-name sytline-connect \
    --query 'Stacks[0].Outputs' --output table
```
`HostVpcId`, `HostSubnetIds`, `HostRouteTableId`, `FunctionSecurityGroupId`, `HostNetworkCidr`, `PlantCidrs` (and
`ApiEndpointId` if created). They then:
1. attach the gateway or transit attachment for the plant VPN to `HostVpcId`;
2. add a route to the plant range in `HostRouteTableId`, targeting that attachment;
3. make plant DNS resolvable from the subnets (so the SyteLine host name resolves to the plant address);
4. confirm the Palo Alto policy allows the function security group's addresses to the web service on HTTP port 80.

Then run the health check (section 5); it should now pass `dns`, `tcp`, `wsdl` and `token`.

> **Adding a setting that both deployments have?** The plant stack (`template.yaml`) and the stand-alone stack (`template-standalone.yaml`) are separate files, so a setting they share must be added to **both** templates (same name, default and allowed values, wired to the same environment variable), to **both** branches of `deploy.sh`, and **once** to the shared block of `deploy.env.example` (a setting only one mode has goes in that mode's block). `tests/unit/test_mode_parity.py` fails, naming the setting, when any of these differ or a variable sits in the wrong block; a setting that only one mode has is never flagged for being absent from the other. See [STANDALONE.md](STANDALONE.md).

## 4. Validate, build, deploy

```
./deploy.sh --profile <govcloud-profile> --validate   # sam validate --lint
./deploy.sh --profile <govcloud-profile> --build      # sam build -> .aws-sam/build (layer + 5 functions)
./deploy.sh --profile <govcloud-profile>              # build + sam deploy, with an interactive change-set review
```

`--profile NAME` (or `AWS_PROFILE_NAME` in `deploy.env`; the flag wins) is passed to `sam build`, `sam validate`, `sam deploy`
and the existing-stack check. `deploy.sh` refuses a profile that `aws configure list-profiles` does not list, and a name with
unsafe characters. With no profile the default credential chain is used (including an exported `AWS_PROFILE`). The profile
is printed at the start of each run so you can see which account you are about to change.

`deploy.sh` stops with a clear message if `deploy.env` is missing or a required value is empty, if the network settings are a partial set, or if create mode lacks `HOST_NETWORK_CIDR`/`PLANT_CIDR_1`. Equivalent raw
commands: `sam validate --lint`, `sam build`, `sam deploy --parameter-overrides 'Key="value"' ...` (quote every value;
list parameters such as subnets are comma-separated inside the quotes).

Review the change set before confirming. On the first deploy expect: the layer, table, API, five functions, and (if
enabled) two VPC endpoints. Later deploys change only what differs.

## 5. Verify after deploying

Stack outputs (API id, function names, table name):
```
aws cloudformation describe-stacks --region us-gov-east-1 --stack-name sytline-connect \
    --query 'Stacks[0].Outputs' --output table
```

1. **Dry-run health check** (no credentials, no login; proves the code loads and the web-service host is reachable):
   ```
   aws lambda invoke --region us-gov-east-1 --function-name <DirectFunctionName> \
       --payload '{"action":"health","dry_run":true}' --cli-binary-format raw-in-base64-out out.json && cat out.json
   ```
   Expected stages: `load`, `dns`, `tcp`, `wsdl`. A failing stage names where connectivity breaks (DNS, routing, security group, VPN).
   **To find out why a stage fails, add `"diagnose": true`** to the payload (`'{"action":"health","dry_run":true,"diagnose":true}'`): the result then carries a separate `diagnostics` section (resolver settings, the ERP name lookup with retries, a connection test to each ERP address, the same for the function's regional AWS endpoint, and plain-language `findings`). It contacts only the ERP host and that AWS endpoint (and the database host when the health check tests the database: see [DATABASE.md](DATABASE.md)) and sends no data or credentials; the stages are unchanged.
2. **Full health check** (logs in with the secret): same call with `'{"action":"health"}'`; expected stages `dns`, `tcp`, `wsdl`, `token`.
3. **API from an approved client** (inside the VPC that has the `execute-api` endpoint, with IAM credentials):
   ```
   awscurl --service execute-api --region us-gov-east-1 -X POST \
       -H 'Content-Type: application/json' -d @order.json \
       https://<ApiId>-<API_VPCE_ID>.execute-api.us-gov-east-1.amazonaws.com/prod/confirmed-orders
   ```
   (request body: `specs/001-syteline-erp-integration/contracts/api.md`). Expect HTTP 202 and an `upload_id`; then
   `GET .../prod/upload-jobs/<upload_id>`. From outside the approved endpoint or without IAM credentials the call must be denied.
4. **Expected outcome while live writes are off:** the upload ends `failed` with code `LIVE_WRITES_DISABLED`, after
   the read-only customer lookup and **before** any number is allocated or any row is written. If the lookup itself
   fails (for example `ERP_UNREACHABLE`), the unconfirmed web-service names in `src/syteline/idos.py` are the first
   thing to check. That is what the discovery task is for.

Logs: `sam logs --stack-name sytline-connect --region us-gov-east-1 --name WorkerFunction --tail`
(also `IntakeFunction`, `StatusFunction`, `SweeperFunction`, `DirectFunction`). Each request writes one structured line
(type, identifiers, outcome, duration). Passwords and tokens are never logged.

## 6. Updating

Change code or `deploy.env`, then run `./deploy.sh` again. SAM rebuilds, shows the change set and updates the stack.
Uploads already stored are kept; the table is not replaced by code changes.

## 7. Enabling live ERP writes (only for an approved test)

There is no test SyteLine. Live writes (number allocation, inserts, note creation) are off by default and must only be
enabled for a test the ERP owner approved in writing, with a reconciliation and cleanup plan
(`docs/reconciliation-runbook.md`; `specs/001-syteline-erp-integration/quickstart.md` step 5).

1. In `deploy.env` set `LIVE_WRITES=true` **and** `LIVE_APPROVAL_REF=<the approval reference>`. `deploy.sh` refuses
   `LIVE_WRITES=true` without a reference.
2. `./deploy.sh`; run the single approved test.
3. Set `LIVE_WRITES=false` (and clear the reference), `./deploy.sh` again, and confirm with a new upload that it ends
   `LIVE_WRITES_DISABLED`.

## 8. Troubleshooting

| Symptom | Likely cause and fix |
|---|---|
| `sam build` fails in `pip install` | pip too old for `--platform`: `python3 -m pip install --upgrade pip`; or no network access to the package index |
| `deploy.sh`: "missing in deploy.env" | fill in the named values |
| `deploy.sh`: "AWS profile ... is not configured" | the name is not in `aws configure list-profiles`; fix the name or run `aws configure --profile <name>` |
| Stack in `ROLLBACK_COMPLETE` after a failed first deploy | `sam delete --stack-name sytline-connect --region us-gov-east-1`, fix the cause, redeploy |
| VPC endpoint creation fails ("private DNS already enabled" or a conflict) | the VPC already has one: set `CREATE_VPC_ENDPOINTS=false` |
| Deployment refused with "Supply all four ..." or "HostNetworkCidr and PlantCidr1 are required ..." | the network settings are a partial set, or create mode lacks its ranges; see section 3a |
| Deployment refused: fewer than two availability zones | the region offers fewer than two zones; the created network needs two |
| `deploy.sh` refuses with "would REPLACE the network" | the existing stack is in the other host-network mode; keep the mode, or pass `--allow-network-change` knowing the functions' network is replaced |
| Worker times out reaching DynamoDB or Secrets Manager | no endpoint or NAT path from the worker subnets: enable `CREATE_VPC_ENDPOINTS` or add a NAT route; check the security group allows HTTPS out |
| `health` fails at `dns` or `tcp` | plant DNS not resolvable from the worker subnets, VPN route missing, or the security group blocks outbound port 80. **With a newly created network this is expected until the network team has done the handover steps in section 3a** |
| `health` fails at `token` | wrong user, or wrong password in the secret; check the secret JSON key is `SYTELINE_PASS` |
| Deploy fails on reserved concurrency | account has under 100 unreserved concurrency: request a limit increase or lower other reservations |
| API call returns 403 | not coming through the approved VPC endpoint, or missing/incorrect IAM credentials |
| Upload ends `LIVE_WRITES_DISABLED` | expected until an approved live test (section 7) |
| Upload ends `needs_reconciliation` | follow `docs/reconciliation-runbook.md`; never resubmit the same order until its records are reconciled |

## 9. Removing the stack

```
sam delete --stack-name sytline-connect --region us-gov-east-1
```
**If the host network was created by the stack, it is deleted too; if the network team attached a gateway or added resources to the VPC, the VPC deletion fails safely, so detach or remove those first.** **This deletes the job table and every stored upload record** (point-in-time recovery is deleted with it). Export anything
you need first. The Secrets Manager secret is not part of the stack and is not deleted.
