# Research: One Function, Always in an Existing VPC

## R1. One entry point, routing by event kind and by `action`
**Decision**: `lambda_function.lambda_handler` classifies the invocation in this order: (1) an explicit non-empty `action` wins; (2) otherwise an **API Gateway REST proxy event** (has `httpMethod` and `resource`) is routed by its resource and method to the existing handler; (3) otherwise the action is `document_event` (feature 006: the IDP event, with the strict refusal of a bare non-event payload). Explicit actions: `health`, `add_note`, `get_notes`, `document_event`, plus the new internal ones `work_upload` (payload `upload_id`), `work_save` (payload `reservation_id`) and `sweep`. An unknown action is `UNKNOWN_ACTION` as today.
**Route table** (`handlers/routing.py`, resource -> handler): `POST /confirmed-orders` -> `handlers.intake`, `GET /upload-jobs/{id}` -> `handlers.status`, `POST /job-reservations` -> `handlers.reserve`, `POST /job-reservations/{id}/save` -> `handlers.save_intake`, `GET /job-reservations/{id}` -> `handlers.reservation_status`. The handlers keep their code, factories and tests.
**Alternatives**: one `action` field in the API request body (rejected: it would change the API's contract, FR-005); separate entry points per function name (rejected: it is the eight-function shape).

## R2. Why the API event is not caught by the default action
**Decision**: an API Gateway event has no `action`, so rule (2) must come before the default of feature 006. A payload that has `httpMethod` but a resource not in the table is answered with an API-shaped 404 (`{"statusCode": 404, ...}`), never handed to the intake. The scheduled cleanup carries an explicit `{"action": "sweep"}` as the rule's constant input (R3), so it needs no classification.

## R3. The cleanup schedule and the self-started background work
**Decision**: the function's `Schedule` event (`rate(5 minutes)`) has `Input: '{"action":"sweep"}'`. The upload intake, the save intake (`savestart.accept_and_start`) and the sweeper start the background work by invoking **this same function** asynchronously (`InvocationType=Event`) with `{"action": "work_upload", "upload_id": …}` or `{"action": "work_save", "reservation_id": …}`; `config.worker_function_name()` returns `WORKER_FUNCTION_NAME` if set, else the runtime's own `AWS_LAMBDA_FUNCTION_NAME`. `handlers/worker.py` exposes `work_upload(payload, context)` and `work_save(payload, context)` (its former `handler` split on `upload_id`/`reservation_id`).
**Alternatives**: SQS or Step Functions to decouple (rejected: new resources for tens of jobs a day).

## R4. The network: three inputs, nothing created
**Decision**: required parameters `WorkerVpcId`, `WorkerSubnetIds`, `WorkerSecurityGroupIds` (no defaults, so CloudFormation refuses a missing one before creating anything; `AllowedPattern` rejects a malformed one) feed the function's `VpcConfig` (subnets and security groups) and the outputs. `WorkerRouteTableIds`, `HostNetworkCidr`, `PlantCidr1..3`, `DynamoDbPrefixListId`, `CreateVpcEndpoints`, `CreateApiEndpoint`, the `Conditions` and `Rules` that supported creating or choosing a mode, and every `AWS::EC2::*` resource are removed. The names keep the plant stack's `Worker*` prefix so existing `deploy.env` files change least (`WORKER_VPC_ID`, `WORKER_SUBNET_IDS`, `WORKER_SG_IDS`). A single subnet is accepted; `deploy.sh` prints a warning that it is not highly available. The VPC ID is validated and reported but the function needs only the subnets and security groups.
**Alternatives**: keep both "supply" and "create" (rejected by the spec); rename to `ATTACH_*` (rejected: more churn).

## R5. The private API
**Decision**: `OrderApi` stays (`PRIVATE`, `AWS_IAM`, resource policy limiting to the endpoint) with `VPCEndpointIds` = the **optional** parameter `ApiVpcEndpointId` (an existing `execute-api` interface endpoint). **Revision: when it is empty there is no API.** Because a SAM function Event cannot be conditional, `OrderApi` and `OrderApiPermission` carry `Condition: HasApi` (`ApiVpcEndpointId` not empty) and the five routes are defined in the API's own `DefinitionBody` as `aws_proxy` integrations to the one function, each with `credentials: arn:${AWS::Partition}:iam::*:user/*` so callers' own credentials invoke it exactly as SAM's Api events did (checked by translating the template before and after: same paths, security, resource policy statements and integrations). The function itself never refers to the API. The endpoint is never created (`MakeApiEndpoint`, `ApiEndpoint` and its security group are removed). API Gateway's own limit (29 s) still applies to those requests (R7).

## R6. Serializing ERP writes without reserved concurrency
**Decision**: `syteline/erplock.py` holds a lease lock in the jobs table: item `LOCK#erp-writes` with `holder` (the invocation's request ID), `expires_at` (now + lease) and `ttl`. `work_upload` and `work_save` acquire it with a conditional put (absent, or expired) **before** claiming the job, poll every 2 s while it is busy up to a wait budget (the remaining time minus the save's minimum budget), and release it in a `finally` only if still the holder. The lease is the function timeout plus 30 s (330 s), so a crashed holder blocks others for at most that long, and a holder that outlives its lease cannot be mistaken for a live one because every write step still runs under the existing claim and the function times out at 300 s. If the lock is not acquired in time the job is left `accepted` / `save_accepted` (nothing was claimed or written) and the sweeper re-drives it. Reserve, health, notes, status and the document event take no lock (the numbering routines are atomic in the ERP, and reads and reservations do not write order data).
No `ReservedConcurrentExecutions` is set on the function.
**Alternatives**: reserved concurrency 1 on the function (rejected: throttles the API and health checks, FR-008); a Lambda-per-purpose via a second function (rejected: FR-003); a DynamoDB transaction per write (rejected: the ERP writes are not DynamoDB writes).

## R7. Per-action time budgets
**Decision**: the function's `Timeout` is 300 s (the longest save). `handlers/routing.py` wraps the context in `Budget(context, seconds)` whose `get_remaining_time_in_millis()` is the smaller of the real remaining time and the budget minus the elapsed time; every handler already reads time through `_remaining(context)`. Budgets: reserve 25 s, intake 12 s, save intake 12 s, status and reservation status 8 s, health 55 s, notes 55 s, document event 55 s (direct or event invokes, not API), `work_upload`/`work_save`/`sweep` the real remaining time. The budgets are constants in `routing.py`, with a test per action.
**Why**: previously each API function's timeout (28 s or less) stopped its work before API Gateway gave up; one function with a 300 s timeout would otherwise keep reserving numbers after the caller already saw a 504.

## R8. The function can start itself
**Decision**: `FunctionName: !Sub "${AWS::StackName}-fn"` is set on the function, and its role has an `lambda:InvokeFunction` statement on `arn:${AWS::Partition}:lambda:${AWS::Region}:${AWS::AccountId}:function:${AWS::StackName}-fn` built from the same string (no reference to the function, so no circular dependency). `EventInvokeConfig.MaximumRetryAttempts: 0` stays (no automatic replay of a reservation or a save).

## R9. One stack, one template
**Decision**: there is one template, `src/template.yaml`, one configuration in `samconfig.toml`, and one deployment in `deploy.sh` and `deploy.env.example`: no second template, no alternate configuration, branch, block or flag, no extra deployment guide, and no test, helper or case that exists for an alternate deployment (`test_mode_parity.py` goes with the other shape checks). Remove the code that existed only for an alternate deployment: `config.require_https`, `allow_http`, `transport_problem`, `plain_http_in_use`, `INSECURE_MESSAGE`, `PLAIN_HTTP_WARNING`; `config.attached`, `config.db_check_mode`, the `SYTELINE_ATTACHED`/`SYTELINE_DB_CHECK` settings and their branch in `health.py` (database stages are decided by `routes.uses_database()` alone); the `ACTION_UNAVAILABLE` branch of feature 006 and the `jobs_table()` availability check; the `INSECURE_TRANSPORT` error use in `client.py` and the notes action. The https-only rule is therefore gone (spec Assumptions); `test_transport.py` keeps only cases about the web-service client itself (those already failing for the missing `zeep` stay failing for that reason).
**Operator note**: a leftover old stack is deleted with `aws cloudformation delete-stack --stack-name <the old stack's name>`; it holds no data.

## R10. The jobs table survives
**Decision**: `JobsTable` gets `DeletionPolicy: Retain` and `UpdateReplacePolicy: Retain` (it does not have them today), keeps its logical ID `JobsTable`, key schema, TTL and point-in-time recovery, so an in-place update of the old plant stack cannot delete or replace it (FR-009, SC-005). A test asserts the logical ID, key schema and both policies.

## R11. Moving an existing plant deployment
**Decision**: `docs/MIGRATION.md` (new) gives two paths. **Supply-mode** deployments (existing network): update the same stack with the new template and new `deploy.env`; CloudFormation creates the one function, repoints the API, removes the seven old functions and the old role policies; the table is retained. **Create-mode** deployments (the stack's own VPC): the network the old stack created is deleted by the update, so first have the network team recreate or take over that network outside the stack (or import it), supply its IDs as the three settings, and only then update; the document warns that updating without doing so would delete the VPC the old functions run in. The order within one update (new function serving before old resources are removed) is CloudFormation's; a `--build`/`--validate` run and the change-set review shown by `deploy.sh` are the safeguard, and `deploy.sh` prints a notice when the existing stack still has the old functions.
**Alternatives**: a script that migrates automatically (rejected: network ownership is the network team's decision).

## R12. `deploy.sh` and the settings file
**Decision**: one deployment: required `SYTELINE_*`, `WORKER_VPC_ID`, `WORKER_SUBNET_IDS`, `WORKER_SG_IDS`; optional `API_VPCE_ID` (empty = no API, always passed so an earlier endpoint is cleared); the optional IDP, database, route, tuning, live-writes settings stay; removed: `HOST_NETWORK_CIDR`, `PLANT_CIDR_*`, `DYNAMODB_PREFIX_LIST_ID`, `CREATE_VPC_ENDPOINTS`, `CREATE_API_ENDPOINT`, `WORKER_ROUTE_TABLE_IDS`, `ATTACH_*`, `ALLOW_PLAIN_HTTP`, `VERIFY_TLS`, `DATABASE_CHECK`; the `--allow-network-change` guard (no create/supply modes exist). A leftover removed setting in `deploy.env` gives a notice naming it and is not passed. The database-login merge into the secret is unchanged. Validation of the three network identifiers moves from the template rules into `deploy.sh` (clear messages) as well as the template patterns.

## R13. What is not touched
**Decision**: the logic of every handler, the IDP source, the numbering and customer routes, the reservation state machine, the event claim of feature 006 and the secret merge are unchanged; their tests keep passing against the new entry point. `verify_tls` (`SYTELINE_VERIFY_TLS`) stays a plant setting as today.

## R14. Test strategy
**Decision**: new tests prove the shape (`test_template_single.py`: exactly one `AWS::Serverless::Function`, zero `AWS::EC2::*` resources, the five routes and the schedule on it, required network parameters, no removed parameters, table retained, role statements, fixed name, no reserved concurrency, timeout 300), the router (`test_dispatch.py`: every event kind and action, the 404 for an unknown route, the strict refusal), the lock (`test_erplock.py`: acquire/contend/expire/release/not-holder, two saves do not overlap with a thread test using a lock-aware fake table), the budgets (`test_budget.py`) and a regression pass that runs each old handler through the new entry point. Removed tests are listed in plan.md.
